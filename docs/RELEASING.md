# 发布流程

## 版本与来源

根 `package.json` 是应用版本的权威来源；四个受管插件随版本同步。tag 必须为 `v` 加完整版本号。使用 SemVer 比较完整预发布段，新版本严格大于当前发布版本；不按字符串或只按主版本比较。

当前更新通道使用 GitHub Latest。版本字符串含 beta 标记与 GitHub 的 prerelease 标志是两件事；变更通道前必须验证版本查询、更新 feed 与已安装客户端。不要为了整理标题改写已发布 tag 或删除历史安装资产。

发布提交必须在受保护主分支中，并有对应提交的质量检查与独立审查。新 push 使旧 SHA 的审查失效；审查失败、超时、缺失或未处理 P0/P1/P2 发现均阻止合并和发布。规则与执行器见 [GitHub 维护说明](github/README.md)。

## 发布前

1. 明确范围及正常、失败、并发、恢复和数据保留的验收条件。
2. 完成源码、锁文件、插件产物和用户文档；运行共享质量门禁。
3. 在隔离数据目录验证 Electron 原生窗口和连接同一服务的浏览器。核对目标二进制、运行时和插件摘要，不能误用旧构建。
4. 覆盖常规任务、长任务、后台工作、重复操作、断连、关闭与安装边界；明确测试限制。
5. 独立 reviewer 检查当前提交。修复后重跑相关检查并重新审查。

```powershell
node scripts/release-quality.mjs
npm run build
npm run prune
npm run dist
```

共享门禁应在干净检出上运行，检查构建是否使受控产物发生差异。本地实现阶段的基本命令见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 发布与更新

PR 通过专用 App 的独立审查和可信质量检查后合并。默认分支 `release.yml` 只按指定 SHA 构建、校验并上传 Actions 产物，权限为只读，不因 tag 自动公开。

使用仓库外已审查的本机发布控制器准备计划。控制器要求候选是当前受保护 master，核对专用 App 身份及签名、可信 workflow 的具体运行与候选 SHA、版本顺序和资产摘要，不执行 tag 自带的发布脚本。

检查计划与公开说明，完成本次发版确认后，显式执行 `release-controller.mjs --head=完整SHA --version=完整版本 --build-run=构建运行ID --publish`。控制器持有本机排他锁，先生成草稿资产，复核远端摘要和最新门禁后公开。完整配置见 [GitHub 维护说明](github/README.md)。

| 资产                      | 用途             |
| ------------------------- | ---------------- |
| `DSH-PX-Setup-<版本>.exe` | Windows 安装程序 |
| `latest.yml`              | 客户端更新 feed  |
| `*.exe.blockmap`          | 差分下载索引     |
| 对应版本 ZIP              | 独立归档产物     |

公开资产使用发布计划列出的规范名称；安装包、blockmap 与更新索引须保持名称一致。版本的 `+` 在资产名中表示为 `_`。

发布说明只写用户可见变化、已知限制和升级影响，不放开发对话、临时路径、PID、原始日志或验收流水账。保留必要依赖归属与法律说明。

发布后在原安装位置通过正式更新通道升级，核对应用版本、运行时清单与插件摘要，检查模型配置、历史会话、批注、定时配置和实际任务。手工替换插件、源码链接或临时开发实例不能替代这一步。

## 故障与回退

正常安装只在任务处理与服务停机完成后开始。不可用的生命周期桥或停止超时进入恢复流程；强制中止必须由用户明确确认，不能作为默认更新步骤。

若迁移失败，按事务日志恢复原 profile 并保留诊断。若需撤回已发布实现，发布版本号更高的修复版本；不要改小版本号、移动 tag 或静默替换已下载资产。应用安装恢复与插件事务恢复是不同层次，不能仅恢复清单就宣称整个安装已回滚。
