# 路线图

## 这里的 beta 指什么

beta 的标准是**与一份普通的 `dsh --profile web` 安装能力持平**，
再加上一个把终端从流程里拿掉的桌面外壳。

这是一条刻意定得很窄的标准，窄到**可以被度量**。
`scripts/verify-capabilities.mjs` 会把两棵树都组合出来并逐行 diff。
一个 beta 版本，就是那次 diff 没有任何缺失行，并且 harness 能在
一台没装 Node 的机器上从随附运行时启动起来。

**beta 范围内**

- 自包含运行时：随附 Node + 官方 dsh + 一份可用的 profile。
- 把 harness 界面嵌进来的桌面窗口，带托盘和干净的退出。
- 随附插件集已安装，并且是通过官方组合包机制参与组合的。
- 机械化的能力平价验证接进了仓库（`npm run verify`）。
- 重启 harness 的能力（因为组合包变动需要重启）。

**明确不在 beta 范围内**

- 代码签名 / 公证（notarisation）。
- 非 Windows 平台的验证（打包目标已配置，但未实测）。
- 任何官方 dsh 没有的 harness 能力。beta 阶段，能力持平是**上限**，不是要去超越的起点。

## beta 之后

### 0. 首启耗时（优先级最高的体验问题）

目前首次启动会把随附运行时（约 690 MB、30 万文件）**同步复制**进用户数据目录，
实测耗时 **4–5 分钟**，期间主进程被阻塞、界面无响应。这是 beta 最明显的短板。

按代价从低到高排的改进方向：

1. **显示进度而不是白屏。** 现在只有一个启动画面。至少应把"正在准备 1/2 …"
   呈现给用户，并把复制进度报出来（`copyProfileTree` 已经逐项处理，接进度很容易）。
2. **异步复制。** 现在用的是同步 `cpSync`，会阻塞事件循环。改为流式异步复制
   （`node:fs/promises` 的 `cp`，或自己实现的队列）即可让界面保持响应。
3. **用目录联接代替复制（Windows）。** `profiles/` 这棵树对每个用户都是同一份只读内容，
   真正的可变状态只在 `sessions/`、`storages/`、`settings.yaml`。
   对只读部分建 Junction 是**毫秒级**的，能把"4–5 分钟"直接消掉。
   必须先验证 dsh 的 fallback 修复逻辑不会试图改写这些链接
   （这正是约束 9 那一类问题的来源，所以要谨慎验证，不能想当然）。
4. **缩小种子树。** 当前 690 MB 里有相当一部分是开发期残留的 fallback；
   一个干净的 `--with-plugins` 全新构建应该更小。

### 1. 自动更新 —— 复用，而不是重造

诱惑是去写一个更新器。别写：这个生态里已经有好几个了，
而且它们已经解决了第一次尝试一定会踩错的各种失效模式。

有两层是独立更新的，把它们混为一谈是典型的错误：

| 层 | 通道 | 机制 |
|---|---|---|
| 桌面外壳 | **GitHub Releases** | `electron-updater`（成熟：差分更新、签名校验） |
| 插件 + profile | **npm** | `dsh plugin add` / `pnpm update`，并协调 `dsh.profile.bundles` |
| `runtime/` 里的 dsh 核心 | GitHub Releases（新的外壳构建） | 跟随外壳 |

值得复用而不是重造的现成插件：

- `dsh-update-checker` —— 双源（npm/GitHub）semver 检查、备份、完整性校验、
  回滚、看门狗式重启、仅回环的写路由、拒绝跨通道的预发布提升。
- `dshmarket` —— 公开了一份带版本的 **Public plugin update API v1**
  （`/dsh-market/api/v1/...`），支持操作轮询、回滚和重启，
  并会校验 pnpm **实际**落盘的那个版本。

正确的分工是：**发布清单**说明这个组合包**应该**包含什么、以及各在什么版本；
**现成的更新器**负责安全地完成安装。

### 2. 分发产物的设计

一份发布清单里值得携带的字段（参考了生态里已被验证的做法）：

```json
{
  "schema": "dsh-px/release/v1",
  "bundle": { "version": "0.2.0" },
  "requiresDsh": ">=0.1.5-rc.2",
  "plugins": [{ "name": "dsh-better-sidebar", "version": "0.19.1", "source": "npm" }],
  "minShellVersion": "0.2.0"
}
```

安装器应当在**触碰**既有安装**之前**先校验 SHA-256 摘要；
下载失败或摘要不匹配必须让上一份安装保持完好且可运行。
重复执行同一条命令，应当表现为原地升级。

### 3. 把插件组合做成一等公民功能

这个应用真正的差异化是那份**精心挑选的组合**，而不是外壳。这指向：

- 一个带版本的**聚合组合包**（生态里已经确立的模式：声明 `dsh.bundle.patch`、
  把成员插件作为依赖锁定、附一份兼容性检查 —— **而不是**复制它们的 patch）。
- 逐插件声明 `dsh.compatibility.dshReleases`，
  好让市场能在宿主版本不匹配**之前**就给出警告，而不是在启动失败之后。
- 用 CI 断言每一个声明的插件名都能在注册表上解析到。
  这不是杞人忧天：这个生态的精选清单里，有四个名字和它们的 npm 包名并不一致
  （`dsh-capability-menu` → `@daweifu/capability-menu`、
  `zhengjy01/dsh-updater` → `@zhengjunyao/dsh-updater`、
  `dsh-suite` → 带 scope 的 `dsh-suite`、
  以及 `@oh-dsh/skins` 在任何注册表上都不存在）。

### 4. 外壳加固

- 单实例锁；已有窗口时聚焦它，而不是再起一个 harness。
- 持久化并恢复窗口几何。
- 把 harness 的 stderr 暴露到一个诊断面板里 ——
  目前插件启动失败只会写到用户已经不再拥有的那个终端里。
- 一个"重启 harness"的入口，因为插件安装需要重启。

## 这个项目坚持的设计准则

1. **外壳从不实现 harness 行为。** 官方 dsh 能做的，外壳就去拉起它或嵌入它。
   能力持平是靠**随附** dsh 达到的，不是靠重新实现 dsh。
2. **能力主张必须被机械验证。** `npm run verify` 会在任何缺失行上失败。
   一条不在 CI 里被检查的主张，就是一条迟早会腐烂的主张。
3. **优先使用官方扩展机制。** 插件组合走 `dsh.profile.bundles`；
   不往树里手工打任何补丁。
4. **优先复用经过验证的组件，而不是自造** —— 尤其是任何带失效模式的东西
   （更新器、回滚、重启监督）。
