# DSH-PX 成熟 Agent 能力审计与路线图

**结论：DSH-PX 已有真实执行任务的基础；距离可长期信任的成熟本机 Agent，最优先的差距集中在执行可靠性、验证可信度、状态一致性与完整工作流。** 本轮通过已安装的 re.0.7 做了 6 轮模型评测、59 次工具调用，结合源码核对和官方产品文档，整理出 **100 项功能规划、18 项问题及改进排期**。

目标保持为：基于 DSH 原生插件范式，整合现成能力并自制缺失组件，交付在本台 Windows 电脑上能完成代码、研究与办公任务的 Agent。工程上可以有很多插件，用户面对的是经过调校、验证的任务能力。

## 已确认的基础与主要差距

已确认能用的部分：Agent 能读取项目规则和源码、识别人工未提交修改、执行多文件修复、保留原测试、补充测试、输出文件产物；Git 面板能查看实际差异。只读模式确实拦截了本轮写入测试，前台命令可以停止，会话刷新后仍保留。见 [E01–E06](evaluations.md)。

当前最影响信任的事实：

1. **本机执行有阻塞。** 默认 `npm test` 在 DSH Windows 沙箱中遇到 `spawn EPERM`；公开网页搜索有效，但正文抓取被本机非公网 DNS 解析拒绝。[B01](findings.md#b01)、[B11](findings.md#b11)
2. **交付状态不一致。** 任务答复已宣布完成，todo 却仍为 1 进行中、6 待处理。用户取消被展示为失败。[B02](findings.md#b02)、[B13](findings.md#b13)
3. **验证还不够独立。** Agent 修复后的 20 项测试全过，但隐藏原型键用例仍失败；另轮审查能发现它，也产生了错误的冻结库存断言。[B09](findings.md#b09)、[B10](findings.md#b10)
4. **自然语言边界没有稳定落实。** 要求只读且不得访问项目外时，模型仍写了 6 个沙箱 TEMP 探测脚本；真正切到只读权限后文件工具被拒绝。前者是约束遵守问题，不能误报为沙箱逃逸。[B08](findings.md#b08)
5. **自制证据层有准确性和规模限制。** 读取历史退出码被误判失败；兼容编辑器 view 被算作文件写入；历史证据受 80 条窗口限制；大输出需要按需获取。[B03–B07](findings.md)

**没有依据给出“成熟度 60%”之类数字。** 功能存在、模型偶尔会用、正常流程可用、异常流程可靠，是不同层级。本报告逐项标注状态和验收目标。

## 评分与阶段如何理解

每一项都有：简介、当前基础、缺口、至少 3 个子项、实现路径、依赖、验收条件、重要程度、实用性、难度、适配度、粗估人日与证据。

| 字段 | 取值与含义 |
|---|---|
| 重要程度 | P0：当前严重阻塞/数据风险，需立即处理；本次未确认 P0。P1：直接影响核心工作或可信交付。P2：高价值增强。P3：可选和低频。 |
| 实用性 | 1 低频小收益；3 特定工作有价值；5 日常高频或决定能否完成任务。 |
| 实现难度 | 1 文案/配置；2 局部明确逻辑；3 多组件整合；4 涉及状态恢复/协议/平台；5 复杂行为和长期验证。越高越难。 |
| 适配度 | 同时考虑 DSH 原生扩展契合度与本机目标：1 偏离目标；3 可做但维护重；5 有明确原生接入点且直接受益。 |
| 人日 | 熟悉代码的单名开发者、可借助 Agent 的粗估，包含实现与基本验证；不含外部等待，不能保证自动化带来固定倍数效率。共用基础使条目不能机械累加。 |
| 状态 | 已有且已实测；部分具备；有基础待验收；未集成或缺失；待确认。状态描述功能基础，不表示该条增强目标已完成。 |

阶段是投资顺序和依赖层级，**30 项短期条目不是一个月的承诺**。建议每周只安排 3–4 个有效开发日的容量，另留回归和真实使用时间；每轮只选 3–6 个紧密相关事项。优先级相同时先处理阻塞实际任务、证据充分、能复用现有基础的项目。

| 阶段 | 数量 | 目标 | 退出标准 |
|---|---:|---|---|
| 短期 | 30 | 让现在已有的编码/研究任务可执行、可信、可恢复 | 本机常用命令与公开正文可用；完成状态一致；核心范围保护、证据分类和 30 类回归可运行 |
| 中短期 | 30 | 补齐常用工作的完整交付链 | 本机完成代码 PR、浏览器修复验证、来源报告、PDF/Word/Excel/Slides 代表任务；每条链都有可检查结果 |
| 长期 | 24 | 支持大型项目、多小时工作、跨日恢复及稳定集成 | 多次压缩/重启/子任务/外部失败下仍保持目标和数据，性能与成本可解释 |
| 远目标 | 16 | 基于真实使用收益选择复杂自主能力 | 先证明收益大于新增复杂度，再进入默认组合；无需一次实现全部 |

## 建议发布批次

以下“批次 A/B”不是已经发布的版本号。单批 8–18 有效人日是起始容量建议；集成失败或上游阻塞时应拆分，不能跳过安装版验收。完成全部短期待办很可能需要多个批次，下一批依据实测重新排序。

| 顺序 | 首批内容 | 可交付结果 | 发布门槛 |
|---|---|---|---|

S15 回归、S21 组合版本、S22 安装升级验收贯穿每一批。**功能分支 → 自动检查及真实任务 → PR → 合入 → tag/Release → 原安装版更新 → 配置/会话/能力复核**继续沿用。此次只增加审计材料、复现脚本和文档，没有应用运行时变更，因此不制造空版本或重新安装；代码修复按上述流程另发功能版本。

## 基于 DSH 插件范式的实现分工

Electron 继续负责生命周期、窗口、运行时和桌面更新；DSH 继续拥有 Agent 轮次、会话、工具执行、权限与持久化。新增能力优先走原生工具/服务/事件、Skills、预设、bundle patch 和现有侧栏扩展点。尤其不能创建另一套不受 DSH 权限管理的执行器来“解决”工具限制。

| 模块边界 | 复用或自制方向 | 对用户的结果 |
|---|---|---|
| 现有 `dsh-px-taskflow` | 修正证据语义，连接 todo/计划/验证，按需获取历史 | 知道任务做到哪里、为何受阻、如何继续 |
| 现有 `dsh-px-workbench` | 入门、模型/命令/网络诊断和可操作恢复建议 | 能配置并检查本机能力；设置里的“运行与帮助”就是这类入口 |
| 现有 `dsh-px-updater` | 组合版本、更新结果、失败恢复 | 升级后仍可使用原项目和会话 |
| 项目上下文与变更保护（建议模块） | AGENTS、搜索、LSP、Git、快照和项目记忆 | 理解项目并保留人工工作 |
| 验证与审查（建议模块） | 独立审查 Skill、验收记录、可重放任务集 | 交付结论有证据，错误能被发现 |
| 浏览器（建议模块） | 成熟驱动接入 DSH 工具、jobs 和 preview | 真的操作网页并验证 UI |
| 产物（建议模块） | PDF/OOXML/数据工具和渲染验收 Skills | 输出可靠的文档、表格、幻灯片和报告 |
| 连接与调度（建议模块） | 原生 MCP/hooks/schedule 逐步整合 | 连接已有工作资料并进行可控自动化 |

“建议模块”只是职责边界，尚非已存在 npm 包；不要求每个功能拆一个插件。先复用已装的 better-sidebar、原生工具和官方服务，确有缺口再自制；组件有价值必须由完整任务证明。

## 每版如何判断进步

用固定正常与异常任务记录：需求完成程度、隐藏验收结果、无关修改保留、越权/范围违反、未证实断言、错误恢复、人工干预次数、耗时、输入/输出/缓存用量。保护约束要求逐次满足；质量指标需重复样例且保留失败记录。

本轮最有价值的基线是：**能做小型多文件任务，也能独立找到遗漏，但仍存在环境阻塞、边界遵守与验证报告可靠性问题。** 下一轮先让这些已知失败变成稳定通过的回归，再扩大默认能力集。完整证据与尚未测试的 30 类场景见 [评测记录](evaluations.md)。
