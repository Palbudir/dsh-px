# 插件分层与组合发行

当前源码为 Pack / Desktop 0.3.2-alpha.1，采用基础部署与五个功能包的分层。可下载版本以 GitHub Releases 为准；版本契约见 [EDITIONS.md](EDITIONS.md)，成员职责见 [PLUGINS.md](PLUGINS.md)。

## 产品方向

主线为 PX Pack 与 PX Desktop 配套交付，Web 连接同一个本机服务并复用功能插件。Pack 是一组经过验证的插件、默认配置与版本组合，不要求对应插件列表中的一个运行时插件。

未修改的官方 Desktop 保留已验证版本的使用说明和既有兼容能力，暂不为后续版本投入专用适配层，也不将其完整安装验收作为每次 PX Desktop 发布的固定门禁。未来恢复投入时重新声明支持范围。避免维护两份功能实现。

继续使用单仓库，维护 Desktop 装配、基础组件、功能包、第三方兼容补丁和组合清单。不因插件拆包立即新增仓库、npm 发布或独立版本矩阵。

## 官方界面的实际分工

锁定宿主 0.2.0-rc.2 的两个入口投影不同信息：

| 入口            | 官方语义                                                              | PX 的对应规则                                            |
| --------------- | --------------------------------------------------------------------- | -------------------------------------------------------- |
| 插件            | 用户安装的组合包、安装自带的可选包，以及主动注册的功能配置页          | 展示可以理解用途并独立选择的能力包                       |
| 设置 → 内置插件 | Loader 运行清单、Agent 预设的会话组件，以及页面模块同步诊断；主要只读 | 保留基础、全局、会话及前端组件的真实来源和运行状态       |
| 常规设置页      | 面向用户的设置、模型、版本及维护入口                                  | 版本更新放版本页；运行诊断放运行与帮助；配置避免重复维护 |

内置插件页不是专门收纳被隐藏项目的文件夹，也不授予组件“官方”身份。组件应根据真实部署方式出现在清单中。不要通过 CSS 隐藏安装项、冒用官方包名或修改运行状态来实现分层。

官方管理器将 profile 直接依赖视为已安装包；installation 供给、非可选且没有错误的组件通常不出现在主列表。基础组件放入 PX Desktop 的安装供给层后，应通过正常装配获得这一行为，保留错误诊断入口。第三方功能不注册到会被标题归为“官方”的配置卡片集合中。

依据为锁定上游的 `packages/boot/plugin-manager/src/index.ts`、`packages/client/ui-plugin-manager/src/client/PluginManagerPage.tsx` 和 `packages/client/ui-settings-plugin-inventory/src/client/index.ts`；升级宿主时重新核对过滤及归属规则。

## 能力分组

采用“基础组件随客户端部署，功能包按能力管理”的 B 方案。下面是用户可见分组，组合包不重复实现执行服务。

| 分组        | 当前能力来源                                                        | 默认入口与行为                                                                  |
| ----------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| PX 基础组件 | workspace 的索引、共享存储和扩展入口；workbench 的公共服务；updater | 内置清单可查；版本和诊断在设置中；不提供容易破坏整套能力的普通总开关            |
| 文件与终端  | 固定版本 better-sidebar 及 PX 集成配置                              | 插件主列表；配置文件、编辑器、终端及变更视图；禁用不等于禁用 Agent 原生文件工具 |
| 执行记录    | taskflow                                                            | 插件主列表；提供执行结果和证据视图；保留可选工作摘要设置                        |
| 产物        | artifacts                                                           | 插件主列表；提供会话交付文件列表及预览入口                                      |
| 引用与批注  | annotations                                                         | 插件主列表；提供引用、批注及草稿插入                                            |
| 定时任务    | schedules                                                           | 插件主列表；提供调度设置与任务管理入口；明确服务离线不执行                      |

功能包内部可继续包含服务、工具和前端等多个组件，详情页沿用官方“包含的组件”结构。默认预装经过验证的组合，用户不必逐项安装才能开始工作。

工作工具栏由稳定的布局基础提供容器，功能包贡献自己的入口。基础层不硬编码一个永远显示全部功能的按钮列表。缺失、停用和加载失败应有准确反馈；移除可选功能不能让其他功能的样式或状态失效。

配置入口使用官方 bundle/row 配置插槽，进入实际任务面板的快捷方式可以保留，但配置数据只有一个所有者。不仅为“有设置页”而制造没有实际用途的选项。

官方“自动化任务”和 PX“定时任务”存在功能重叠。拆发行前对照触发、目标会话、权限、持久化、取消和离线语义；能复用的部分优先复用官方服务。未完成数据迁移和行为核对前，不删除已有 PX 定时配置或同时触发两套调度。

## 元数据与模块规范

- 用户名称、用途和图标遵循官方包元数据：`locale/en.json`、`locale/zh.json` 的 `meta` 字段，以及 `package.json` 的资源导出和 `icon`。
- 主标题是功能名称，包名、组件 ID 和来源是次要信息；完整本机模块路径不充当产品名称。
- 成员使用精确包名引用。文件路径会被原生元数据读取器跳过；包导出子路径虽然能提供元数据，却不满足当前前端模块发现的精确包名规则。
- 安装先由原生管理器完成解析表更新，再启动宿主；包名入口须覆盖干净安装、离线重启、升级和热启用。
- 基础与功能包之间显式声明依赖；停用时解释影响，重启或升级不悄悄重置用户选择。
- 尽量保留组件 ID、配置定位与业务存储位置；确需变更时提供迁移映射。

## 社区插件的接入与维护

当前随 Pack 交付的社区插件只有 `dsh-better-sidebar` 0.24.1。它不是首次启动时从插件市场自动安装的最新版，也不是直接使用本机已有的同名插件。

当前构建过程是：从 npm 固定地址取得发布归档 → 校验 SHA-512 SRI → 解包为构建目录中的独立副本 → 校验原始宿主文件 SHA-256 → 应用 PX 认证兼容补丁 → 校验补丁后 SHA-256 → 放入 Pack 的 `bundledDependencies` → 通过组合包 patch 注册到原生宿主。

补丁在原有来源检查之外接入原生 Connection 请求认证。修改仅发生在构建副本，原始社区归档、用户安装目录和包管理器共享缓存不被改写。来源和补丁由 `src/shared/sidebar-auth-compatibility.ts` 固定，打包由 `scripts/build-native-pack.ts` 执行。原包名、版本和 MIT 许可保留。

维护规范：

1. 记录来源仓库、准确版本、下载地址、完整性、许可、修改内容及兼容宿主，不自动追随 latest。
2. 详情页明确“社区插件”与上游作者/项目；有 PX 修改时显示兼容补丁标识，不声称原版未经修改。
3. 优先无修改集成；必要适配保存在可审查补丁中，范围扩大后再决定是否维护明确的 fork。
4. Pack 锁定经过组合测试的版本；用户单独安装同名或其他版本时先识别归属和冲突，不覆盖其配置，也不加载两个提供相同服务的实例。
5. 禁用、卸载与升级分别定义；禁用不删除数据，社区更新需重新核对补丁和实际功能。

`dshmarket`、`dsh-mermaid-render`、`dsh-find-plugin` 仍是待适配项目，不算当前已交付成员。CodeMirror 等普通依赖库不计入功能插件数。

## Pack 与 Desktop 的安装更新调整

Pack 逐步成为带精确版本、依赖和摘要的组合交付物，Desktop 在宿主启动前通过原生包管理操作安装匹配的能力包。保留一个组合安装入口，无须让用户手工装齐五个包。

基础组件随 Desktop 的 installation 层装配；可选能力在 profile 中独立管理。Pack 保留 tgz 交付格式，增加 distribution.json 和六个组件归档。Desktop 消费组合清单并移除旧受管聚合入口；独立 Web 可使用同一归档的聚合入口，两种入口不能同时注册。

更新分工：Desktop 控制宿主、窗口、基础部署和整套预装组合；功能包只在声明兼容的范围内更新。首阶段自制能力仍跟随同一 Pack 版本，社区版本独立锁定，不立即扩大成多个独立发布节奏。

迁移必须保留用户声明、禁用状态、模型凭据、会话、批注和定时记录；移除旧入口不删除业务数据。多包安装失败时能恢复上一套一致配置并重试，避免半新半旧。失败恢复策略必须在真实安装器与隔离 profile 上验证。

版本遵循 [EDITIONS.md](EDITIONS.md)：0.3 使用新的组合安装协议，Pack 与 Desktop 共用代际 3；Desktop 清单明确允许从代际 2 升级。DSH 上游版本独立锁定。

## 维护与验收

- 样式使用显式归属和引用计数，随所属 Cordis effect 释放。反复启停其他插件时，工作工具栏仍须避开原生标题栏；不能依靠刷新恢复。
- 插件主列表、内置运行清单、中文元数据、启停与依赖反馈均需实际界面检查。
- 选句批注需验证来源、现有草稿保留、保存后插入、失败重试、切换会话与停用组件；不自动发送。
- 升级需验证旧配置及业务数据保留、无重复注册/调度、安装失败恢复和进程中断重试。
- 发布覆盖 PX Desktop、连接它的 Web 和聚合 Web 入口；原版 Desktop 不做固定全量验收。
- 候选稳定后对精确提交进行一次独立 DS Flash 审查，后续只复核新增或未解决部分。已有有效证据不重复跑。
