# DSH-PX 产品目标与交付标准

DSH-PX 的目标是在本台电脑上提供成熟 Agent 的工作能力。用户提出需求后，应能看到项目被理解、任务被执行、修改被验证、结果被交付；卡住或中断时知道原因并能继续。Codex、Cursor、Trae Work 是用户提出的能力参照，不作为本项目已经达到同等水平的声明。

DSH 原生插件范式是实现基础。我们负责选型、调校、集成并自制缺失能力；用户无需先理解插件系统。插件数量、开关数量和“自由组装”不是产品验收指标。

## 能力分工与当前证据

| 用户需要 | 当前基础 | 还需验证或建设 |
|---|---|---|
| 理解项目与约束 | DSH 文件搜索、读取、AGENTS 指令、Skills | 大项目定位准确率、相关上下文选择与跨会话复用 |
| 执行完整修改 | DSH 标准预设、文件编辑、PowerShell、后台任务 | 多文件修改、失败修复、依赖安装与长任务的场景验收 |
| 计划与任务推进 | DSH todo、plan、goal、子任务 | 模型使用稳定性、阻塞识别、取消与恢复的组合行为 |
| 检查结果 | DSH 工具输出、文件交付；现有侧栏的文件变动面板 | 更直接的变更审阅、验证覆盖说明与审阅反馈闭环 |
| 继续工作 | DSH 持久会话和上下文压缩 | 中断副作用核对、后台进程状态重建、多日运行 |
| 本机持续使用 | Electron 自带运行时、已有安装器和更新链路 | 每版回归、故障恢复与安装后真实任务 |

## re.0.7：任务交接与执行证据

自制 `dsh-px-taskflow` 插件增加会话侧栏“任务进展”与两个 Agent 工具：

- `task_review`：读取当前会话已有的工具调用、结果、文件工具涉及路径和最近交接点；无需 Agent 自行回忆执行结果。
- `task_checkpoint`：记录目标、进展、下一步及实际调用编号。引用必须能在近期日志中找到已结算结果，允许记录失败复现，拒绝编造编号、进行中或未知结果。
- 侧栏通过已装的 `dsh-better-sidebar` 扩展服务注册，沿用 DSH 原生右侧栏。关闭该社区插件会移除面板，但 Agent 工具仍可使用。
- 工作记录直接保存在 DSH 的工具结果事件中，重启后从原会话恢复，不另建任务数据库。冷读取使用官方只读持久句柄，释放句柄，不抢占写入权限。
- 工作流提示要求多步骤实现任务先检查项目约定与既有修改，保留无关改动，使用原工具执行、验证并交付；它不覆盖计划模式或权限策略。简单问答和小修改可以不创建交接点。

“Agent 工作记录”是模型总结；执行记录是系统事实。“已返回”不等于测试通过；“待检查交付”不等于人工验收完成。当前面板显示最近 80 条执行、最多 200 个文件工具路径，长输出截断并提示。命令行造成的文件改动仍应在 Git/文件变动面板审阅；没有 Git 时不能把文件工具路径清单当作完整差异。

任务记录之后发生任何新执行，面板会提醒记录可能已过时。重启不会自动重放可能有副作用的操作，也不会自动启动新的模型请求；用户在原会话继续即可读取交接点。

## 开发顺序

后续按照真实任务失败点推进：先完善修改审阅和验证，再建设项目上下文复用与长任务恢复，最后扩展更复杂的工具集成。每个阶段都需在已安装应用里完成具体任务；不以设置页展示、插件加载成功或一次玩具示例替代成熟度验收。

固定流程：功能分支 → 自动测试与真实任务 → PR → tag 与 Release → 原安装版更新 → 配置、会话与能力复核。当前仅要求本机可用；现有 CI 保留，不扩展分发目标。
