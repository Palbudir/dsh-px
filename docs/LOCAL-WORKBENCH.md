# DSH-PX 本机工作台（re.0.6 验收）

> re.0.7 已将本页入口改为“设置 → 运行与帮助”，运行诊断默认折叠。新任务能力与产品标准见 [PRODUCT.md](PRODUCT.md)。以下保留 re.0.6 历史记录。

更新日期：2026-09-22。验收范围是这台 Windows 电脑；仍严格通过功能分支、PR、版本 tag、Release 和已安装应用更新交付。

## 现在怎样使用

1. 从原有 DSH-PX 快捷方式启动已安装应用，通过设置里的 DSH-PX 分区检查更新并安装 `0.1.0-beta.re.0.6`。
2. 打开 **设置 → 本机工作台**，输入项目文件夹的完整路径，点击 **添加工作区**。也可继续使用 DSH 原有的目录选择器。
3. 关闭设置，选择刚添加的工作区，用 **标准模式** 和已配置的模型创建会话。工作台提供三种可复制的任务提示词。
4. Agent 完成后检查文件、工具输出与交付物。首次验证可先用空目录运行“验证工具可用”。
5. 插件仍通过原有 **插件市场** 管理。更改组合包后，等待任务结束，在工作台确认 **重启本机服务**。

日常数据继续使用 `%APPDATA%\dsh-px\dsh-home`，不会迁移到仓库。更新后继续使用原快捷方式，不需要源码仓库或新的启动脚本。
端口优先为 3080，占用时自动顺延。原 3080 服务保持运行时，桌面版会选择 3081。
托盘的“在浏览器中打开”现在使用当前服务签发的认证入口，避免首次打开浏览器遇到 401。

## 新增能力与实现边界

- **独立插件 `dsh-px-workbench`**：遵循 `dsh.bundle.patch`、宿主 `apply/inject` 和 `dsh.client` 约定。界面通过官方 `settings.section` 插槽注册，使用宿主 React。
- **路径添加工作区**：调用官方 `workspaceController.create({ path })`，由 DSH 负责去重、验证和持久化，没有另建工作区存储。写端点要求自定义请求头，避免跨站简单请求触发操作。
- **运行检查**：显示实际 Node、数据目录权限、PATH 中的 Git/pnpm、插件安装版本与组合包声明。凭据只检查文件是否存在，不读取或返回密钥。检查结果不冒充模型连通性测试或插件运行健康检查。
- **服务恢复**：有心跳和明确状态；同一时刻只执行一次重启；等待旧服务退出并清理其工具进程后再启动。异常退出显示本地恢复页，可重试、打开日志或数据目录。sandbox preload 改为 CommonJS，与 Electron 当前配置一致。
- **配置保留**：刷新只替换 DSH-PX 自管插件文件。已有设置、凭据、Cordis 补丁和第三方依赖保留。安装版会备份 profile 清单，通过官方 CLI 将两个自管插件接入安装资源；自管插件不再依赖源码链接。
- **插件安装修复**：修复物化 home 后 `.modules.yaml` 中仍指向种子 `.pnpm` 的路径；只替换确切的种子引用，并通过独立文件替换避免改写种子的硬链接。保留用户自定义 store。
- **日志**：解析分块启动输出，认证 token 不写入新日志；诊断缓冲区有长度上限。此变更不会追溯清除旧日志。

外壳负责桌面窗口、进程和恢复；DSH 继续负责模型、会话、权限、工具、预设、Skills 和插件市场。

## 已安装版本升级

首次启动新安装版时，先保留旧 profile，再通过官方 `dsh plugin add file:... --offline --ignore-scripts` 安装资源内的自管插件并协调 bundles。
迁移只在种子身份变更后运行一次，失败不会写完成标记，重启可重试。profile 清单、锁文件和补丁预先备份在 home 下的 `backups/plugins-*`；不声称 pnpm 失败能完整自动回滚依赖目录。
开发态仍允许源码链接；它只是验证环境，不作为交付完成的标准。安装版迁移使用本机现有 pnpm 与缓存。

## 尚未覆盖

本轮完成的是可直接在本机使用的一次产品升级，不代表所有长任务场景已经验收。
恢复页已实现，但本轮没有通过原生桌面自动化点击其 IPC 按钮；异常状态与动作桥重启经过实际验证。
长任务中途取消、所有权限审批分支、任意第三方插件安装失败的回滚，以及连续多日运行仍需后续验证。
原生目录选择器在此次浏览器自动化中未取得可操作对话框，因此新增了可直接输入路径、走官方控制器的入口。
正式发布后必须通过原安装版验证更新、安装路径与版本号；结果记录在对应 Release 验收文档中。
