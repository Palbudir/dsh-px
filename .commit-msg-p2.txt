feat(首启): 物化改用硬链接，首启从 4–5 分钟降到 5.7 秒

## 问题
首次启动用同步 `cpSync` 把随附运行时（约 620 MB、1.4 万项）整树复制到用户
数据目录：实测 4–5 分钟，期间界面完全冻结（连"在干活"都看不出来）。

## 改动
新增 `src/main/materialize.ts`，把物化改成：
1. **硬链接**（`linkSync`）——同卷内不复制数据。实测 13833 个文件 **5.7 秒**、
   几乎不额外占盘。
2. **让出事件循环**——每 400 项 `setImmediate`，主进程不冻结。
3. **进度页**——`main()` 改为先建窗口显示进度，再物化、再起 harness；
   进度按 120 ms 节流推送"已处理 N / 总计 M"。用普通页面而**不是模态框**，
   与"更新交互不打断用户"的既定原则保持一致。
4. **幂等续传**——每项先查目标是否存在，中途失败可续跑；
   完成判据同时核对标记**与** profile 清单，避免"标记写了但被中断"时带着空壳启动。

## 实现中踩到并修掉的四个真实缺陷
1. **开发态插件变成悬空链接，静默消失**
   原样重建 Junction 会在用户机上留下指向**构建机源码仓库**的链接，harness 报
   `Cannot find package 'dsh-px-updater'`。正确规则是分两类：指向随附 dsh 安装
   目录内部的链接原样保留（dsh 断言 fallback 必须是链接），其余解引用成真实内容。
2. **Windows 上按 Dirent 判定链接类型 → 按"文件"建目录链接而失败**
   对 Junction，`readdirSync({withFileTypes:true})` 的 `entry.isDirectory()` 是 false
   （Dirent 走 lstat 语义）。据此调 `symlinkSync(..., 'file')` 会 ENOENT，
   并且当时那个空 `catch` 把它**吞掉**了，只留下一个不存在的链接。
   改为按 `statSync().isDirectory()` 判定，并让失败如实抛出。
3. **硬链接数达上限时直接中断首启**
   NTFS 单文件硬链接上限 1024；种子树文件来自 pnpm 内容寻址 store，每装一个项目
   多一条链接，实测本机某文件已有 623 条 —— 这正是本机首启失败的原因
   （Windows 报 `UNKNOWN: An attempt was made to create more links …`）。
   原实现只白名单了 `EXDEV` 等几个错误码，其余直接抛错。
   改为**任何**链接失败都回退复制，连复制也失败才中断；回退次数与样本写入标记文件。
4. **`existsSync` 跟随链接** → 悬空链接被当成"不存在"，续传时重复创建而 EEXIST。
   改用 `lstatSync` 判定目标是否已存在。

## 测试
新增 `npm run test`（esbuild 打包 + `node --test`，4 个用例，含真实触发硬链接
上限并验证回退复制）。这也是本项目第一次有单元测试：上述缺陷 1、2 端到端冒烟
只能表现为"插件消失"，很容易漏掉。

## 实测
| 指标 | 原 | 现 |
|---|---|---|
| 首启物化 | 4–5 分钟 | **5.7 秒** |
| 首启到 harness 监听 | 4–5 分钟 | **约 14.6 秒** |
| 二次启动 | 秒级 | 约 7 秒（物化完全跳过） |
| 额外磁盘占用 | 一份完整副本 | ≈0 |
